# SPEC-20260524-WP-7.2 — HNSW Persistence (mmap)

> **Priority:** 🔴 HOCH — Löst den zentralen RAM-Engpass  
> **Dependency:** WP-4.1 DONE (mmap-Pattern bewiesen in SSTables)  
> **DONE-Definition:** 4 Tests bestehen 3×. Cold-Start < 100ms bei 100K Vektoren.  
> **Assigned:** Jules Account 03 (index)  
> **Erstellt:** 2026-05-24

---

## Ziel

Den HNSW-Index (Graph-Struktur + Vektordaten) auf Disk persistieren und via
memory-mapped Files laden. Eliminiert:
1. **RAM-Bottleneck**: Vektoren liegen auf SSD, OS Page Cache managed RAM
2. **Cold-Start-Penalty**: Kein Rebuild via `collection.load_index()` nötig
3. **Doppelte Speicherung**: `StoredDocument.embedding` wird obsolet

---

## Strategischer Kontext

Auf dem Ziel-System (8GB RAM, Ryzen 3500U) limitiert der aktuelle HNSW-Ansatz
die praktische Kapazität auf ~200K 1536-dim Embeddings (f32) bevor OOM.
Mit SQ8 steigt das auf ~800K, aber der Graph-Overhead (Connections) addiert ~800MB.
mmap-Persistence verschiebt die Grenze auf die SSD-Kapazität (typisch 256GB+).

---

## Design

### Dateiformat: `.hnsw` Flat File

```
[Header: 64 bytes]
  Magic:         4 bytes  "HNSW"
  Version:       4 bytes  u32
  Dimension:     4 bytes  u32
  Node Count:    8 bytes  u64
  Max Layer:     4 bytes  u32
  Entry Point:   8 bytes  u64
  Quantized:     1 byte   bool
  Reserved:      31 bytes

[Quantizer Block: variable] (nur wenn quantized=true)
  Min Values:    dim * 4 bytes (f32)
  Max Values:    dim * 4 bytes (f32)

[Node Array: node_count * node_size bytes]
  Per Node:
    DocId:        8 bytes  u64
    Max Layer:    4 bytes  u32
    Vector:       dim * 4 bytes (f32) ODER dim bytes (u8 bei SQ8)
    Connections:  Per Layer:
      Count:      4 bytes  u32
      Indices:    count * 8 bytes (u64)

[Connection Index: node_count * 8 bytes]
  Offset ins Node Array für Random Access
```

### API

```rust
impl HnswIndex {
    /// Persists the current index to disk.
    pub async fn save(&self, path: &Path) -> Result<()>;

    /// Loads an index from a persisted file via mmap.
    /// Vectors are NOT copied into RAM — OS Page Cache manages access.
    pub async fn load(path: &Path, config: HnswConfig) -> Result<Self>;

    /// Returns true if the index is loaded from disk (mmap-backed).
    pub fn is_persistent(&self) -> bool;
}
```

### Memory Model

- **Write Path**: Neue Inserts gehen in einen In-Memory `TxBuffer` (Status Quo).
  Bei `commit()` werden sie in den HNSW-Graph eingefügt UND an das `.hnsw`-File appended.
- **Read Path**: `search()` traversiert den mmap-backed Graph. Hot Nodes werden vom
  OS Page Cache im RAM gehalten. Cold Nodes werden on-demand von SSD geladen.
- **Rebuild**: Bei > 20% Deletions wird der Graph komplett neu geschrieben (compact).

---

## Invarianten

1. **Boundary-Check** vor jedem mmap-Offset-Zugriff
2. **`unsafe` nur für `Mmap::map()`** mit `// SAFETY:` Kommentar (analog `sstable.rs`)
3. **Atomic Write**: Neues File → rename (kein in-place Overwrite)
4. **Backward-kompatibel**: `HnswIndex::new()` funktioniert weiterhin rein in-memory
5. **Thread-safe**: `Arc<Mmap>` für concurrent Readers (analog `SstableReader`)

---

## Nebeneffekt: StoredDocument Entschlackung

Nach Implementierung von WP-7.2 kann `StoredDocument.embedding: Vec<f32>` entfernt werden.
Embeddings werden ausschließlich im `.hnsw`-File gespeichert. Dies reduziert die
LSM-Storage-Größe um ~75% (bei 1536-dim f32: 6KB pro Doc → ~200 bytes Metadata).
