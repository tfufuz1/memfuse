# SPEC-20260508-WP-5.1-Checkpointing

## 🎯 1. Das Ziel (Context & "Why")
> **Status:** ✅ DONE
Implementiert Native State Checkpointing (Time-Travel) für Agenten-Status basierend auf MVCC und WAL-Sequenznummern. Erfordert einen "Checkpoint-Pinning"-Mechanismus im LSM-Compactor, um verknüpfte Segmente (SSTables) vor vorzeitiger Garbage Collection aufzubewahren, solange Checkpoints existieren.

---

## 🛡️ 2. Die Invariante(n) (The "Law")
- **[INV-CHECKPOINT-1]**: *Checkpoint Pinning*: SSTables und verknüpfte Tombstones in `memfuse-store` dürfen nicht vom Compactor gelöscht werden, solange ein persistenter Checkpoint auf ihre `seq_no` verweist oder älter ist.
- **[INV-CHECKPOINT-2]**: *Single Source of Truth*: Checkpoints referenzieren strikt existierende WAL `seq_no`s in der Engine, ohne Daten zu duplizieren.

## 🛑 4. Definiertes Fehlerverhalten (Fail-Cases)
- Wenn ein Rollback auf einen Checkpoint angefragt wird, der nicht existiert -> `Err(MemFuseError::CheckpointNotFound)`.
- Wenn ein Checkpoint erstellt werden soll, dessen `seq_no` in der Zukunft liegt oder ungültig ist -> `Err(MemFuseError::InvalidSequenceNumber)`.

---

## ✅ 5. Der TDD Checkpoint (Red-Phase Vorgabe)
- Der Test muss nach einer Serie von Inserts einen Checkpoint bei `seq_no = X` anlegen.
- Weitere Inserts und Deletes werden ausgeführt, um Daten zu überschreiben, und eine manuelle Compaction wird getriggert.
- Der Test muss verifizieren, dass Datensätze, die vor `seq_no = X` gültig waren, aufgrund des **Checkpoint-Pinnings** NICHT gelöscht bzw. Garbage-Collected wurden.
- Ein Rollback auf den Checkpoint-Namen muss die Datenbank exakt in den Zustand von `seq_no = X` versetzen (Time-Travel).
- Nach Löschung des Checkpoints und erneuter Compaction müssen die veralteten SSTables / Tombstones endgültig gelöscht werden.
