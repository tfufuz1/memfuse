# Atomic Spec: WP-5.5 — Repair-on-Open Registry (P0)

> **Status:** DONE
> **Author:** MemFuse Conductor  
> **Priority:** 🔴 CRITICAL (Sovereign Core Protection)

## 1. Problemstellung
Wenn MemFuse während einer Schreiboperation abstürzt, kann es passieren, dass Daten bereits im **WAL/LSM-Store** (`memfuse-store`) festgeschrieben wurden, der **HNSW-Index** (`memfuse-index`) aber noch nicht aktualisiert wurde. Beim nächsten Start wäre der Index unvollständig („Split-Brain“).

## 2. Lösungsansatz: Repair-on-Open
Beim Initialisieren einer `Collection` wird eine Integritätsprüfung durchgeführt:

1. **Last Index SeqNum**: Der HNSW-Index speichert im Header die letzte erfolgreich verarbeitete `TxId` (Sequenznummer).
2. **LSM State Check**: Wir fragen den `LsmStorage` nach der höchsten bekannten `TxId`.
3. **Replay-Logik**: Wenn `Lsm_TxId > Index_TxId`:
   - Scanne alle Einträge im LSM-Store ab `Index_TxId + 1`.
   - Füge die fehlenden Vektoren in den HNSW-Index ein.
   - Führe einen `commit()` auf den Index aus.
4. **Checkpointing**: Erst nach erfolgreicher Reparatur wird die Collection für User-Anfragen freigegeben.

## 3. Technische Details

### 3.1. Index Header Erweiterung
In `crates/memfuse-index/src/persistence.rs` (HnswHeader) wird ein Feld `last_tx_id: u64` (8 Byte) hinzugefügt.

### 3.2. Registry-Mechanismus in `memfuse-db`
In `crates/memfuse-db/src/collection.rs` wird die Methode `Collection::repair()` implementiert, die vor dem ersten Zugriff aufgerufen wird.

## 4. Akzeptanzkriterien (TDD)
- [ ] **Test Case 1 (Crash Simulation)**: Ein Test schreibt 100 Vektoren in den Store, bricht aber vor dem Index-Update ab.
- [ ] **Test Case 2 (Auto-Repair)**: Beim erneuten Öffnen der Collection müssen 100 Vektoren im Index vorhanden sein.
- [ ] **Test Case 3 (Zero-Debt)**: Keine Warnungen in Clippy, keine `unwrap()`.

## 5. Invarianten
- **[INV-DB-REPAIR-1]**: Der Index darf niemals eine höhere `TxId` haben als der Store.
- **[INV-DB-REPAIR-2]**: Während der Reparatur ist die Collection für Read/Write gesperrt.
